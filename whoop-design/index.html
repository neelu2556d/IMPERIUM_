Architecture

Where WHOOP data flows

The browser never sees the WHOOP client secret or tokens. OAuth, token exchange/refresh, and all data reads happen on our server; normalized readings are stored per-user behind row-level security and rendered into the screens below.

01 · Connect

OAuth 2.0 consent

Member approves scopes on WHOOP. We exchange the code for tokens server-side and request offline for silent refresh.

→
02 · Sync

Server-side read

We pull /v2/recovery, /v2/activity/sleep & /v2/cycle, normalize, and upsert one row per local day into wearable_data.

→
03 · Surface

Dashboard + AI

Readings render in the member's dashboard and, optionally, into their own connected AI assistant via a read-only MCP endpoint.

Beyond the dashboard

AI briefing & data handling

🤖 Optional AI assistant (member-initiated)

  • Members can connect their own AI assistant (e.g. Claude) to a read-only endpoint.
  • It reads only that member's own WHOOP sleep, recovery & strain to answer "should I train hard today?" and produce a daily briefing.
  • Scoped per-user by row-level security; no WHOOP data is shared across users.
  • Never used for advertising, profiling, or sale. The member can revoke access at any time.

🔒 Security & privacy

  • All WHOOP calls + token exchange/refresh run server-side; the browser never sees the client secret or tokens.
  • Tokens stored per-user under row-level security — no user can read another's data.
  • WHOOP API is v2 only; reads gated on score_state === "SCORED".
  • Disconnect deletes our stored tokens; the member can also revoke from WHOOP settings.
